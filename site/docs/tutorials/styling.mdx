**tremolo-ui ships no CSS.** A component renders its markup, keeps track of the
value, and handles the pointer, keyboard and wheel; what it looks like is
yours. Style it with vanilla CSS, CSS Modules, Tailwind, CSS-in-JS — whatever
the rest of your app already uses.

## 🎨Your classes, on every part

**No class names are shipped.** Every part takes a `className`, and what you
pass is the only class it carries — nothing of ours is there to be overridden,
and no stylesheet of ours can reach in.

```jsx
<Slider.Root className={theme.root} value={value} min={0} max={100} onChange={setValue}>
  <Slider.Track className={theme.track}>
    <Slider.Thumb className={theme.thumb} aria-label="Level" />
  </Slider.Track>
</Slider.Root>
```

`style` works the same way, and the parts that draw more than one element take
a `classes` object for the pieces inside them — `Slider.MarksOption` has
`classes={{ mark, label }}`, and `Piano` reaches its keys through `keyProps`.

The theme below is written as CSS Modules for exactly this: each file exports
one class per part, and you wire them up as above.

## 🚦State

State is on the element as an attribute, not as an extra class, so it is a
selector away. **A state that is off leaves no attribute behind**, so the
attribute alone is the selector — there is no `="false"` to match by mistake.

Each component lists the attributes of every part on its own page, under
**API Reference** — [Knob](/docs/components/Knob/#api-reference),
[Slider](/docs/components/Slider/#api-reference),
[XYPad](/docs/components/XYPad/#api-reference),
[NumberInput](/docs/components/NumberInput/#api-reference),
[Piano](/docs/components/Piano/#api-reference) and
[PointsEditor](/docs/components/PointsEditor/#api-reference). The ones you
will reach for most are `[data-disabled]` and `[data-readonly]`.

The controls that are one in their own right — `Knob`, `NumberInput.InputField`,
the steppers, and the range inputs inside a thumb — carry the matching ARIA as
well (`aria-disabled`, `aria-readonly`). Those say what the control *is*;
the `data-` attributes are what the styles read.

```css
.slider[data-disabled] {
  opacity: 0.5;
}
```

`:focus`, `:hover` and `:focus-within` work as they would anywhere, since the
focusable element is a real one.

## 📐Custom properties

Anything about a component that is a matter of appearance is a custom property,
and the prop that goes with it does nothing but write that property.

```jsx
<Slider.Track thickness={16} />
// is exactly
<Slider.Track style={{ '--thickness': '16px' }} />
```

So the prop, a stylesheet and an inline style are three ways to say one thing,
and the usual cascade decides between them. **The default is in the CSS, not in
the component**, so a rule of yours is enough to change it everywhere — you do
not have to pass a prop to every instance.

```css
.track {
  --thickness: 16px;
}
```

A number passed as a prop is taken as pixels; anything else is written through
as-is, so `'3rem'`, `'100%'` and `'auto'` all work.

Which properties a part has is listed on its own page, under **API
Reference** — [Knob](/docs/components/Knob/#api-reference),
[Slider](/docs/components/Slider/#api-reference),
[XYPad](/docs/components/XYPad/#api-reference),
[NumberInput](/docs/components/NumberInput/#api-reference),
[Piano](/docs/components/Piano/#api-reference) and
[PointsEditor](/docs/components/PointsEditor/#api-reference).

A theme adds variables of its own on top of those — the one below has
`--thumb-size`, the track's `--axis`, and the colours of each kind of key.
Those are the theme's to name, and they are only there because it reads them.

## 📋The theme used on this site

Every example in these docs is styled by the files below. They are the starting
point rather than a dependency: copy the ones you need into your own project
and edit them.

Each is plain CSS with no build step, and each one leans on custom properties
(`--knob-size`, `--thumb-size`, `--active-color` …) so the common changes are a
one-line override.

**They say what the parts look like, not where they go.** A component places
its own parts — a thumb is taken out of flow and centred on the value by the
component itself — so a theme of your own cannot put one in the wrong place by
leaving a rule out. Where that placement has room for taste, it reads a custom
property: `--translate` on a thumb, a mark or a point moves it off its centre.

### Dark mode

The theme reads whatever marks the page: `.dark` on an ancestor, or
`[data-theme="dark"]`, which is what this site and Storybook set.

```css
:global(.dark) .thumb,
:global([data-theme='dark']) .thumb {
  --color: oklch(64.5% 0.17548 266.373);
}
```

They are two selectors rather than one because a CSS Module leaves `:global`
where you write it. Swap them for however your own app says dark — a class of
your own, or `@media (prefers-color-scheme: dark)` if it follows the system.
